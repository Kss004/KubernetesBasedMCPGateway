## Findings

### N6. Note: the IP lock counts every failure from the shared IP, and a successful login does not clear it
In 6a the 5th wrong attempt already returned 429, not the 6th. The IP key already held a failure from earlier in the 15-minute window: `success()` clears only the name key (`cc44fe8`, `session.ts`), and on kind every client is `172.18.0.1`. That works as designed, but two consequences need documenting:
- **Lockout of a named account:** anyone who knows a user name (for example `A`) can keep that account locked by failing 5 times a minute. This is the usual trade-off; write it in the threat model.
- **Prod IP, unverified:** behind Traefik on k3s with the klipper service load balancer, the last `X-Forwarded-For` hop may be a node or load-balancer address rather than the real client, unless `externalTrafficPolicy: Local` (or Traefik's forwarded-headers trust) is set. In that case the IP lock is shared by everyone, as it is on kind. Check this in the prod rehearsal, or document it.

### N7. LOW: the Audit tab shows "No calls yet." before the first fetch
`apps/dashboard/src/Audit.jsx:63` renders the empty state while `rows` is still the initial `[]`, so a fresh load briefly says "No calls yet." even with 101 rows. This is the same race fixed for the Servers tab in N5 (d72369c). Show "Loading…" until the first fetch finishes.

### N8. Note: one "orders today" answer said there were no orders
The tester's run returned `list_orders ✓` with "No orders came in today. The query returned an empty list.", while order 47 had just been created. My rerun minutes later was correct (12 orders). Most likely the model passed a wrong `after`/`before` range. That cannot be confirmed, because tool arguments are deliberately not logged (D22). It is a model error, not invented data (the tool really ran). Optional hardening: have the gateway compute the "today" range itself, or validate list_orders date arguments against the store day.
