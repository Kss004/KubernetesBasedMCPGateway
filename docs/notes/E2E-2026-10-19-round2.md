## Still failing

### H1. HIGH: a follow-up turn still sometimes answers without calling the tool
- **Repro** (A, fresh chat each run):
  1. "Get the details of order 26" → `woo get_order ✓`.
  2. Then "What orders came in today?"
- **Runs:**
  - Run 1 (create product, then orders today) and run 2: `list_orders ✓`, answer correct (#35, #32, #30, #28, #26, #24).
  - Run 3: no chip. The reply listed #32 $15.00, #31 $30.00, #29, #27, #30 $50.00, #28 $80.00 and #26, "7 orders total, $230.00". All made up.
  - Run 4: no chip. The reply listed "#25 $10000.00 Test Lamp" and "#26 $20.00". Made up.
- **Audit (checked myself):** `woo__get_order` at 11:21:32 and 11:22:38 is followed by no `woo__list_orders` row. The only list rows are 11:19:46 (run 1) and 11:20:45 (run 2).
- **Conclusion:** the stricter system prompt (d91b9a3) is not enough for `qwen/qwen3.8-27b`. The model still answers from earlier conversation text about half the time.
- **Fix options (session1 to choose and explain):**
  1. **Gateway guard:** if the final reply of a turn mentions store data (order numbers, prices) and no tool ran in that turn, discard it and either ask the model again ("call a tool") or return "I could not look that up, try again". This is deterministic and testable with the mocked LLM.
  2. **Force a tool call:** set `tool_choice: "required"` on the first LLM call of a turn. Trade-off: chit-chat turns also call a tool. It could be limited to questions that mention orders, products or prices.
  3. **Cut what the model can copy:** send earlier assistant turns to the LLM as a short summary or truncated text, so there are no old numbers to reuse.
  - Option 1, perhaps with option 3, gives a guarantee without changing the UX. Add a unit test: a scripted LLM that answers without a tool call must not reach the user unchecked.

## New, low
- **N1:** `HEAD /`, `/app.js` and `/style.css` return 404 while GET returns 200 (`curl -sI http://app.localhost/`). Some health checkers and link checkers use HEAD. Treat HEAD like GET without a body.
- **N2:** `apps/gateway/src/chat.ts:129` marks the 429 retry as `// shortcut:`. AGENTS.md requires `// ponytail:` (naming the ceiling and the upgrade path, which the text already does).
- **N3:** Recovery took 31.4s after scaling back to 1. The backoff caps at 30s, so once a server has been down for a while it can take up to about 30s to be seen again. Either accept and document it (fine for the demo), or cap recovery probing at 10s.
- **N4:** `chat.ts:254` and `:312` log `error=${message}`. That is safe today, but the upstream error text is free-form. Consider truncating it, and make sure it never echoes tool arguments (D22).
- **N5 (unverified):** on first load the Servers tab briefly showed "No servers registered" while the rows were rendering. It might be a render race; check whether the empty state appears before the first fetch finishes.
