## Remaining (not blocking; for docs or a later fix)

### R1. MED, design limit: the H1 guard is narrow
It is deterministic and works for the observed failure. Three gaps remain (`chat.ts:177`, `:193-214`):
- **Once any tool has run in the request, the final reply is never checked.** For example, the model calls `get_order` and then invents a list of today's orders: nothing stops it. A stricter rule would require that the specific tokens shown (order numbers, amounts) appear in this request's tool results.
- **The regex only catches `#123`, `$`/`€`/`£` amounts and `N.NN`.** Made-up plain integers ("3 orders waiting", "Order 39 shipped", "USD 25") are not caught.
- **A legitimate repeat of earlier data without a new tool call** ("what was the total of that order?" → "$45.00") gets the nudge, and if the model still doesn't call a tool, the fallback. That is safe, but slightly annoying.
- **Suggestion:** document it as a known limit in `docs/threat-model.md` / design-tradeoffs (prompt plus regex guard plus audit trail). Tightening it to "tokens must appear in this turn's tool results" is a later improvement.

### R2. Demo risk: the Groq rate limit
3 of 6 runs in about 6 minutes hit the rate limit even with the one retry. The user then sees the chip followed by `[error: the model is rate-limited, try again in a few seconds]`. For the demo video, pace the chat prompts (about 30s apart) or use a key with a higher limit. Cosmetic: the friendly text is still wrapped as `[error: …]`; show it as plain text.

### R3. LOW: the `dist/` folders are stale
Gitignored build output from before 6a4d6f9 (e.g. `apps/gateway/dist/chat.js`) still holds the old code. It is harmless because images build from source, but `npm run build` or a clean would avoid confusion.
