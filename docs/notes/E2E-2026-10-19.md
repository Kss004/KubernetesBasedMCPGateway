## Findings

### H1. HIGH: a chat follow-up turn can return made-up store data without calling any tool
- **Repro** (A, one conversation):
  1. "Create a product called Test Lamp priced 20.00" → `create_product ✓`.
  2. Then "What orders came in today?"
- **Actual:**
  - The reply was "3 orders today, all completed: #18 $16.74 1× Ceramic Mug … #20 $58.64 2× Stainless Bottle … #17 $44.26 Brass Lamp, PayPal."
  - None of these orders or products exist, and the real order #26 was missing.
  - No tool chip appeared, and there is **no audit row**: the last row is `woo__create_product` at 10:41:28Z.
- **It is intermittent:**
  - The same question in a fresh chat called `list_orders` and was correct.
  - A second follow-up attempt ("details of order 24" → "orders today") did call the tool, but then hit M2.
- **Likely cause:**
  - The system prompt only says "Use tools when needed" (`apps/gateway/src/chat.ts:41`).
  - History is sent as plain text with tool calls and results removed (`apps/dashboard/src/Chat.jsx:27`). So the model sees earlier answers full of data with no tool use behind them, and copies that pattern.
- **Suggested fix:**
  - Tighten the system prompt: store facts (orders, products, prices, statuses) may only come from tool results in the current turn; for any order or product question, call the tool again; never answer from memory or from earlier turns.
  - Optionally keep a short "[called woo__list_orders]" marker in the history text.
  - Add a unit test for the prompt text.

### M2. MED: an LLM 429 is not handled
- **Repro:** after several chat turns in a few minutes, Groq returned 429. The chat showed the raw text `[error: llm 429]` right after `woo list_orders ✓`.
- **Actual:**
  - No retry.
  - No friendly message.
  - Nothing in the gateway log. `kubectl logs deploy/gateway-gateway` has had 1 line ("gateway on :3000") for the pod's whole life.
- **Fix:**
  - On 429, wait once using `retry-after` (capped at about 10s), then retry. Mark it `// ponytail:`, since a retry library is not allowed.
  - Show "The model is rate-limited, try again in a few seconds."
  - Log every LLM and tool failure to stdout. This overlaps the known "chat failures are not logged" item.

### M3. MED: detecting Unreachable takes about 31–34s, not the documented ~10s
- **Repro:**
  1. Run `kubectl -n urumi-upstreams scale deploy/upstreams-everything-mcp --replicas=0`.
  2. Poll `/api/upstreams` every 1–2s.
- **Actual:** Connected until 31s (run 2) and 34s (run 1). The pod was deleted at once (`terminationGracePeriodSeconds: 10`).
- **Expected:** about 10s, per D24 (5s interval, 2s timeout, 2 failures). docs/notes earlier recorded about 15s.
- **Where:** `apps/gateway/src/pool.ts:76-86`.
- **Hypotheses:**
  - After the 1st failure, `skipUntil = now + 5000` while the interval is also 5000, so the next tick can see `now < skipUntil` by a few ms and skip one round.
  - Probes may also still succeed while the pod is terminating.
- Recovery is fine: Connected 8s after scaling to 1.

### L4. LOW: chat tool chips disappear from earlier messages
- **Repro:** send two messages. The first reply's chip (for example `woo list_orders ✓`) vanishes when the second is sent.
- **Cause:** `Chat.jsx:27-29` rebuilds `msgs` from `history`, which keeps only `{role, content}` and drops `tools`.
- **Fix:** keep the previous `msgs` objects for display, and strip `tools` only in the request body.

### L5. LOW: chat shows markdown as literal text
The replies contain `**Test Lamp**` and `- ` lists, which display as raw asterisks. Either render a tiny safe subset (bold and lists, as escaped text nodes), or tell the model to use plain text. The current prompt says only "never raw HTML".

### L6. QUESTION: an unreachable server's tools stay in `tools/list` and in chat
While everything-mcp was Unreachable, `/api/tools` still listed 11 tools. The model then called `everything__add` and got "server unreachable". Is that intended (cached listing, clear error per C2), or should Unreachable tools be hidden like Disabled ones? Please decide and document it in design-tradeoffs.

### L7. LOW: members calling admin APIs get 401, not 403
`/api/servers`, `/api/users`, `/api/keys` and `/api/upstreams` return 401 to a logged-in member (`adminAuth` in `index.ts`). It should be 403 for an authenticated non-admin.

### L8. LOW: the `/mcp` 401 has no `WWW-Authenticate` header
The body is `{"error":"unauthorized"}` with no `WWW-Authenticate`. MCP clients use that header for auth discovery. This ties into the still-unverified Claude Code item (T3.7). Consider `WWW-Authenticate: Bearer realm="urumi"`.

### L9. LOW: smoke-script checks can mislead
- `scripts/smoke.sh:26-27`: "every enabled upstream is Connected" needs `node` on PATH. From a non-interactive WSL shell (nvm not loaded) it prints FAIL even though everything is Connected. Check for `node` and say so, or parse with `grep`/`jq`.
- `scripts/smoke.sh:28`: "credentials never returned" passes without testing anything if the token or auth fails, because it greps a 401 body. Assert a 200 first.

### L10. LOW: dashboard assets have no `Cache-Control` and unhashed names
`/`, `/app.js` and `/style.css` come with no `Cache-Control`. After a redeploy, browsers may run a stale dashboard because of heuristic caching. Send `Cache-Control: no-cache` (simplest), or use hashed file names.

### L11. LOW: key Revoke has no confirmation
Remove server asks for confirmation, but Revoke key (Team & Keys, both tables) does not. One misclick kills a client's key.

### L12. LOW: `get_order` exposes `order_key`, and the model repeats it
In "Get the details of order 24" the reply included `Order key: wc_order_…`. The order key opens the order-received page. Drop `order_key` (and similar fields) in woo-mcp's `get_order` output.
